# Release Playbook — null0x686F Mod Suite

How releases actually work across the 4 mod repos + this hub. Written 2026-07-30 from the real workflow files and git history, not from a plan — if this drifts from the YAML, the YAML wins; fix this doc, not the other way around.

## Repos & dependency order

- **`PZmodB42_null0x686F-CoreLib`** — shared library, no dependencies. Every other mod's `mod.info` has `require=null0x686F_CoreLib`.
- **`PZmodB42_null0x686F-QoL`**, **`PZmodB42_null0x686F-ContextCleaner`**, **`PZmodB42_null0x686F-CombatText`** — depend on CoreLib at PZ load-time (`require=`), no version pin. There's no CI-enforced ordering; the dependency is conceptual (release CoreLib first when a change to it is expected to affect consumers), not mechanical.
- **`PZmodB42_null0x686F-Suite`** (this repo) — not a mod. Hosts the reusable `mod-release.yml` workflow every other repo calls, plus this doc.

## Version bump rules

Fully automated via [release-please](https://github.com/googleapis/release-please), driven by [Conventional Commits](https://www.conventionalcommits.org/) on `main`. Config per repo: `release-please-config.json` (`release-type: simple`, `bump-minor-pre-major: true` — since all 4 mods are pre-1.0, `feat`/breaking commits bump minor, `fix` bumps patch, matching semver's pre-1.0 convention) + `.release-please-manifest.json` (tracks current version).

**Never hand-edit `modversion=` in a committed `mod.info`.** It's synced from the release tag at build time (see Pipeline step 4) — PZ's `mod.info` parser has no comment syntax, so a release-please version marker committed into the file renders as raw garbage in the in-game mod list (confirmed in-game 2026-07-28). The committed `mod.info` never carries the real version; only the zipped release artifact does.

## Changelog format

`CHANGELOG.md` per repo, generated by release-please from commit messages. It **prepends** a new section under the file header and never rewrites the sections below it — measured on the `v0.4.0` commit, which touched only the 7 lines it added. So an older section can be corrected by hand without release-please fighting you, but never hand-write a *new* heading: it appends, it doesn't dedupe.

**Which commit types reach the changelog is declared, not defaulted.** Each repo's `release-please-config.json` carries an explicit `changelog-sections`. Under release-please's defaults, `refactor`, `ci`, `docs`, `chore`, `test` and `style` are hidden, which silently dropped real work (the QoL `modoptions` split and the `OnBreak` rework were both `refactor:` and left no trace).

**Visible and releasable are the same switch.** Measured 2026-08-03: making every type visible caused a lone `chore:` commit to open a `0.4.1` release PR. There is no "shows in the changelog but doesn't cut a version". So the list is split on *does this change what the player gets*:

| Visible — and cuts releases | Hidden — and cuts nothing |
|---|---|
| `feat` `fix` `perf` `refactor` `build` `revert` | `docs` `ci` `test` `style` `chore` |

Consequence to expect: a `docs:`-only or `chore:`-only push to `main` produces **no** release PR. release-please's log says so out loud — `No user facing commits found since <sha> - skipping`. That is the correct outcome, not a broken pipeline.

## Branch strategy

- **`main`** — stable. Two independent mechanisms guard it, don't confuse them:
  - *Classic branch protection* (`required_approving_review_count: 0`, `enforce_admins: true`, no bypass) — active on **CoreLib and ContextCleaner** only. QoL and CombatText are unprotected. The old rule of thumb here was "protected once it ships its first Workshop item"; that no longer describes reality — QoL has shipped (`3774429809`) and is still unprotected, so treat this list as measured state, not as a policy that maintains itself.
  - *Ruleset* `main: promocao so por merge commit` — targets `refs/heads/main` on all 4 repos with `allowed_merge_methods: ["merge"]` and no bypass actors. This is what mechanically prevents the squash described under Promotion below. No bypass **on purpose**: the repo owner is the only person who merges here, so an admin bypass would exempt the one account the rule exists for.
- **`dev`** — integration branch, unprotected. Every push builds a pre-release under the floating `dev-latest` tag (see Pipeline, dev path) so in-progress work is testable without cutting a real version.
- Floating tags `latest`/`dev-latest` are moved via `git tag -f` + `git push --force` inside CI, not by hand.
- **`feature/<Story-ID>/<short-desc>`** (Story ID optional but recommended, e.g. `feature/AGGY-0011/module-refactor`; falls back to `feature/<short-desc>` with no Story yet) — new work, branches from `dev`.
- **`chore/<short-desc>`** — maintenance, no feature logic, branches from `dev`.
- **`bugfix/<Story-ID>/<short-desc>`** — non-critical bug found during development, branches from `dev`, follows the normal test-then-promote cycle like `feature/`.
- **`hotfix/<short-desc>`** — critical bug in an already-published mod (currently: CoreLib, ContextCleaner). Always branches from `main` directly, bypassing whatever unfinished work sits in `dev`, since `dev`→`main` promotion could otherwise drag along unrelated in-progress features. After merging to `main`, merge (or cherry-pick) the same fix into `dev` so it isn't lost there.
- Never encode the Epic ID (`PZHZ-0X`) in a branch name — the repo itself already identifies the epic (e.g. `corelib` = PZHZ-01), so it adds no information. Use the Story ID (`AGGY-XXXX`) instead when one exists.

## Promotion — the merge method is load-bearing

Two different merges, two different methods. Getting the second one wrong is not a style preference; it breaks release-please and disconnects the branches.

| Merge | Method | Why |
|---|---|---|
| `feature/*`, `fix/*`, `chore/*` → **`dev`** | **squash** | collapses work-in-progress into one clean Conventional Commit. The PR title becomes the commit message, so it must itself be conventional. |
| **`dev` → `main`** | **merge commit**, never squash | release-please reads each commit on `main`. A squash replaces N commits with one, so only the PR title survives. |

**What a squashed promotion actually costs** (measured 2026-08-03, QoL and CoreLib):

- *The branches silently diverge.* A squash writes a brand-new single-parent commit, so the original commits never become ancestors of `main`. `dev` reads as permanently ahead even though its code shipped. QoL sat at 17 commits "ahead" whose content diff against `main` was two files — `CHANGELOG.md` and `.release-please-manifest.json`. The same 17 commits were re-listed in four consecutive `dev`→`main` PRs (#25, #27, #29, #30), which is what "my commits aren't reaching main" looks like from the outside.
- *The changelog collapses.* QoL's `0.4.0` described 14 commits with the single line `* big refactor`.
- *The version comes out wrong.* CoreLib's post-`v0.3.0` commits were `fix`/`perf`/`ci`/`docs`/`chore`/`refactor` — no `feat` anywhere, so it was a patch. It was squashed under the title `feat: luacheck gate and singlefile logger`, release-please read `feat:` and bumped **minor**: `0.4.0` instead of `0.3.1`. Published versions don't go backwards, so that one is permanent.

**Always merge with an empty body:**

```bash
gh pr merge <N> --merge --delete-branch --body ""
```

GitHub otherwise copies the PR title into the merge commit body, and release-please parses it as a second Conventional Commit — the same change lands in the changelog twice, once for the merge commit and once for the original. Both `CoreLib 0.3.0` (two identical `vendor PZAPI ModOptions patch` lines) and the transient QoL `0.4.1` release PR show the artifact. The merge commit's *subject* is safe on its own; release-please logs `commit could not be parsed` for `Merge pull request #N from …`. It's the body that does the damage.

**Recovering a branch pair that already diverged this way:** confirm the only differences are release-please's own bookkeeping (`git diff --stat origin/main origin/dev` → `CHANGELOG.md` + `.release-please-manifest.json` and nothing else, in particular zero `.lua`), push the current `dev` to a `backup/` ref, then reset it onto `main`. Merging instead of resetting is the trap: it makes `main` an ancestor of `dev` but leaves the stale commits pending, so the next promotion re-announces already-released work.

## Commit conventions

[Conventional Commits](https://www.conventionalcommits.org/), full type list (not just the 4 used so far):

| Type | Use for |
|---|---|
| `feat` | new feature or capability |
| `fix` | bug fix |
| `docs` | documentation only |
| `style` | formatting, no logic change |
| `refactor` | code change that's neither a fix nor a feature |
| `perf` | performance improvement |
| `test` | adding or correcting tests |
| `build` | build system or dependency changes |
| `ci` | CI/CD workflow changes only (no mod code) |
| `chore` | maintenance, no production code change |
| `revert` | reverts a previous commit |

Scope (`type(scope): ...`) is optional. Existing commits scope by mod name (e.g. `chore(corelib):`) but that's redundant since each mod has its own repo — only use a scope in this hub repo (`suite`) if a commit needs to disambiguate between its scripts/docs/workflows.

## Pipeline — what fires on what ref

1. **Push to `main`** → `release.yml` runs `release-please-action`. If there are unreleased Conventional Commits, it opens/updates a release PR (title `chore(main): release X.Y.Z`) with the version bump + changelog. Nothing ships yet.
2. **Merging that PR** → release-please tags the real commit (`vX.Y.Z`) and sets `release_created: true`, which triggers the `publish` job → calls this repo's reusable `mod-release.yml`.
3. **Push to `dev`** → `dev-release.yml` force-moves the `dev-latest` tag to the new commit, then also calls `mod-release.yml` with `tag_name: dev-latest`, `publish_steam: false`, `prerelease: true`. No release-please involvement on `dev`.
4. **`mod-release.yml` (reusable, this repo)** — the only place a mod's shipped version and Workshop state actually change:
   - Rewrites `modversion=` in the CI checkout's `mod.info` from the tag (never touches the committed file).
   - Zips `Contents/` → GitHub Release asset.
   - Creates the GitHub Release (`softprops/action-gh-release`).
   - If `publish_steam: true` — verifies the Workshop item already exists via the Steam Web API (first publish is always manual through Steam's own client; CI only re-publishes an existing item), then publishes via `lucashort7/steam-workshop-deploy@v3` with `path: 'Contents'` (critical — the whole repo as root silently ships a broken content tree, see Gotchas) and `previewFile` set.

## Gotchas (confirmed in production, not theoretical)

- **Content root**: the Workshop item root must be `Contents/`, not the repo root — shipping the whole repo (README, CHANGELOG, `release-please-config.json`, etc.) with the mod nested a level deeper inside is a silently-valid-but-broken upload (no CI error, mod just never appears in the in-game mod list). Already fixed via `path: 'Contents'`; don't regress it.
- **`previewFile` isn't supported by the upstream deploy action** at all — that's why `lucashort7/steam-workshop-deploy` (our own fork) exists. If a future repo's `release.yml` is scaffolded from an older example, confirm it points at `lucashort7/steam-workshop-deploy@v3`, not `m00nl1ght-dev`'s original.
- **`previewFile` is relative to the repo root, not to `path`** — the fork's own two docs contradict each other (`README.md:113` says repo root, `action.yml:61` says relative to `path`). Settled by measurement, not by reading: `mod-release.yml` passes `path: 'Contents'` while `preview.png` sits at the **repo root** in CoreLib and ContextCleaner, and both publish with a working thumbnail. The README is right; `action.yml`'s input description is the stale one and is still worth correcting upstream in the fork. (Noted in passing: QoL has no `preview.png` at its root at all, so its thumbnail is whatever was set manually at first publish.)
- **First Workshop publish is always manual** (via the in-game Steam client) — CI can only update an item that already exists, confirmed by the "Verify Steam Workshop item exists" step failing loudly instead of silently creating a new item.
- **Steam API can return a transient "Service Unavailable"** on publish — `gh run rerun --failed` resolved it last time (ContextCleaner `v0.2.1`), not a real failure worth debugging further.
- **`dev` can drift behind `main`** if a hotfix lands straight on `main` — check `git log dev..origin/main` before opening a `dev`→`main` PR to avoid an unmergeable promotion PR.
- **A `dev` branch can also hold work that never shipped.** As of 2026-08-03, ContextCleaner and CombatText each have 4 real commits on `dev` (AGGY-0020's i18n and orphan-tab removal; AGGY-0019's migration off self-registering events) that are not on `main`, so they are not released and not on the Workshop, however finished they look elsewhere. Unlike the QoL/CoreLib divergence above, those two differ in **actual Lua**, so they need a real promotion — never a reset. The measurement that separates the two cases is `git diff --name-only origin/main origin/dev | grep '\.lua$'`.
- **A release PR that no longer applies stays open.** When a config change makes previously-releasable commits non-releasable, release-please logs `No user facing commits found - skipping` and simply stops updating the release PR it had already opened — it does not retract it. Close it by hand, or you'll merge a stale version bump later.

## Manual steps this pipeline does NOT cover

- First-time Workshop submission for QoL/CombatText (Steam client only).
- Deciding CoreLib-first release ordering when a change spans repos — release-please has no cross-repo awareness, this is a judgment call.
- Noticing that a release-please PR is open and merging it — nothing currently polls for this across the 4 repos.
